Executive Summary

Codex is in strong shape from a security standpoint. Every SQL statement audited across all four workspace packages and the server uses parameterized queries; the only dynamic SQL fragments are compile-time constants, typed table-name unions, or ?-placeholder lists. CSRF protection is layered (session-bound token with timing-safe comparison, Sec-Fetch-Site rejection, and an Origin allowlist), admin authorization is enforced server-side on every admin route via Clerk session-claim metadata, and per-user data scoping is applied consistently inside the SQL itself (clerk_user_id / account_id predicates on every read and write). The WoR image import pipeline is notably hardened: HTTPS-only host allowlist, redirects disabled, magic-byte content validation, a 10 MB size cap, multi-layer path-traversal defenses, and SVG served with a sandboxing CSP. No Critical or High security findings were identified.

The most important finding is a High-severity reliability / data-loss risk: the WoR import pipeline permanently deletes users' per-account collection rows whenever an entity disappears from the upstream Fastidious catalog, and catalog shrinkage is only a non-blocking warning in validation — a single bad upstream fetch can irreversibly destroy user ownership data. Two Medium findings follow: a stale WoR import lease permanently blocks admin imports after a process crash (the TTL is never consulted on the admin path and there is no force-release endpoint), and the Warframe sync executes large synchronous SQLite transactions on the event loop. The remainder are Low/Informational improvements in typing, duplication guarding, test coverage of orchestration code, and client polish.

Security Findings (2 Low, 1 Informational)

LowDone Fastidious demon slug is not URL-encoded or charset-restricted before use in fetch path and cache filename

server/import/wor/fastidiousClient.ts:42-48  •  server/import/wor/fastidiousCatalog.ts:226-251

Description
sanitizeCacheSlug() only rejects /, \, and ... Characters such as ?, #, %, &, and spaces pass through. The slug — untrusted data parsed from a Fastidious HTML page — is then interpolated directly into the request path and into a cache filename:

// fastidiousClient.ts
export function sanitizeCacheSlug(slug: string): string | null {
  const trimmed = slug.trim();
  if (!trimmed || trimmed.includes('/') || trimmed.includes('\\') || trimmed.includes('..')) {
    return null;
  }
  return trimmed;
}

// fastidiousCatalog.ts (loadDemonDetail)
const detailPath = path.join(cacheDir, 'demon-details', `${safeSlug}.json`);
...
const { page } = await fetchFastidiousInertiaPage<DemonShowProps>(`/demons/${safeSlug}`);

Impact
A malicious or malformed slug can inject query-string or fragment components into the outbound GET (host is fixed to fastidious.gg, so exposure is limited), and characters like ? are invalid in Windows filenames, causing cache writes to throw and abort demon-detail processing.

Recommendation
Restrict slugs to a safe charset (e.g. /^[a-z0-9_-]+$/i) in sanitizeCacheSlug() and/or apply encodeURIComponent(safeSlug) when building the route path.

Low Session ID and CSRF token are not rotated when a different Clerk user binds to an existing session

server/session/worSessionBinding.ts:19-26  •  server/session/epic7SessionBinding.ts:19-26  •  server/index.ts:205-246

Description
When a session previously bound to one Clerk user is reused by another (e.g. shared browser, user switch), the binding helpers clear the game-account fields but keep the same express session ID and the same stored CSRF token:

export function ensureWorSessionBoundToClerkUser(req: Request, clerkUserId: string): void {
  const sessionData = getWorSession(req);
  const boundUserId = sessionData.clerk_user_id;
  if (boundUserId && boundUserId !== clerkUserId) {
    clearWorSessionFields(req);   // fields cleared, but session ID / csrfToken survive
  }
  sessionData.clerk_user_id = clerkUserId;
}

Impact
Low in practice — authentication is carried by the Clerk cookie, not the express session, and the session only stores CSRF state and account selection. Still, session-fixation hygiene says privilege/identity changes should rotate the session identifier and CSRF secret.

Recommendation
Call req.session.regenerate() (and re-issue the CSRF token) when the bound Clerk user ID changes.

packages/core/src/auth/clerk.ts:7-9  •  packages/core/src/middleware/auth.ts:47-58

Reliability Findings (1 High, 1 Medium, 3 Low, 1 Informational)

HighDone WoR import permanently deletes users' collection rows when the upstream catalog shrinks

server/import/wor/startupPipeline.ts:362-402  •  packages/games/wor/src/db/queries.ts:262-289  •  server/import/wor/validateCatalog.ts:16-50

Description
Every import deactivates catalog entries missing from the fetched bundle and then hard-deletes all account rows tied to inactive or unknown catalog entries — including rows the user marked as owned, with their awakening/promotion gauge progress:

// startupPipeline.ts (inside the import transaction)
const deactivated = deactivateStaleCatalogEntries(db, bundle);
...
const pruned = worQueries.pruneInactiveCatalogAccountRows(db);

// packages/games/wor/src/db/queries.ts
const heroes = db.prepare(
  `DELETE FROM account_heroes
     WHERE catalog_hero_slug IN (SELECT slug FROM catalog_heroes WHERE active = 0)
        OR catalog_hero_slug NOT IN (SELECT slug FROM catalog_heroes)`,
).run().changes;

Catalog shrinkage is only a non-blocking warning in validation, so a partial upstream response sails through:

// validateCatalog.ts — shrinkage produces level: 'warning', which does NOT fail validation
if (bundle.heroes.length < MIN_HEROES) {
  issues.push({ level: 'warning',
    message: `Expected at least ${MIN_HEROES} heroes, found ${bundle.heroes.length}.` });
}

Impact
A single flawed Fastidious fetch (partial page render, upstream A/B change, temporary removal of heroes) marks the missing entities inactive and irreversibly destroys every user's ownership and gauge data for them in the same transaction. There is no soft-delete, backup, or restore path. The empty-bundle guard in deactivateMissingSlugs (early return when keepSlugs.length === 0) only protects against a fully empty category, not partial shrinkage.

Recommendation
Either (a) soft-delete: keep account rows for deactivated catalog entries and hide them in queries, so a later import restores them with progress intact; or (b) make shrinkage beyond a small tolerance a validation error that aborts the import (requiring an explicit force flag to proceed); ideally both. A pre-import backup of the account_* tables would also cap the blast radius.

MediumDone Stale WoR import lease blocks all future imports — TTL is never consulted on the admin path and there is no force-release

server/import/wor/adminImportJob.ts:75-124  •  server/import/wor/importLease.ts:15-55  •  server/routes/worAdminApi.ts:95-116

Description
tryAcquireWorImportLease() supports stealing leases older than 60 minutes, but the admin start path never reaches it: both the route (isWorImportRunning()) and startWorAdminImport() bail out first on isWorImportLeaseHeld(), which checks only whether lock_token is set and ignores locked_at/TTL:

// importLease.ts — no TTL check
export function isWorImportLeaseHeld(db: Database.Database): boolean {
  const row = db.prepare('SELECT lock_token FROM import_lease WHERE id = ?').get(LEASE_ROW_ID) ...
  return Boolean(row?.lock_token);
}

// adminImportJob.ts — refuses before the TTL-honoring acquire is ever attempted
if (isWorImportLeaseHeld(db)) {
  return { started: false, reason: 'Import lease held by another process', ... };
}

Impact
If the process is killed mid-import (crash, OOM, power loss), the row keeps its lock_token forever. Every subsequent admin import returns 409 indefinitely — the 60-minute TTL never applies, and unlike the Warframe sync (which has POST /admin/sync/release-lease), the WoR import has no force-release endpoint. Recovery requires manual SQLite surgery or an empty catalog at boot (only then does the startup pipeline hit the TTL-honoring acquire).

Recommendation
Make isWorImportLeaseHeld() treat leases older than IMPORT_LEASE_TTL_MINUTES as not held (matching the acquire predicate), and/or let startWorAdminImport() attempt tryAcquireWorImportLease() directly instead of pre-checking. Adding an admin force-release endpoint mirroring the Warframe one (refusing while an in-process import runs) is a good complement.

LowDone Warframe sync lease has the same TTL-ignoring gate (mitigated by force-release endpoint)

server/services/warframeSyncState.ts:20-34  •  server/services/warframeSyncJobs.ts:296-302

Description
isWarframeSyncRunning() returns true whenever warframe_sync_lease.lock_token is set, ignoring the 30-minute TTL that tryAcquireWarframeSyncLease() honors. acquireWarframeSyncSlot() throws before attempting acquisition, so a crashed process's stale lease blocks syncs past its TTL.

Impact
Same deadlock pattern as the WoR lease, but recoverable: an admin can call POST /api/warframe/admin/sync/release-lease, which correctly refuses while an in-process sync is running.

Recommendation
Align isWarframeSyncLeaseHeld() with the TTL predicate so recovery is automatic rather than requiring manual admin action.

LowDone Source hashes are persisted as "processed" before the import validates and commits

server/import/wor/startupPipeline.ts:247-259

Description
Immediately after fetching the Fastidious pages — before overrides, image download, validation, and the catalog upsert transaction — the pipeline records the new source hashes on disk and in catalog_meta:

const result = await fetchFastidiousCatalog({ live, ... });
...
const refreshedHashes = computeCurrentSourceHashes(cacheDir);
writeProcessedSourceHashes(refreshedHashes);   // marked processed before the import succeeds
updateSourceHashesInDb(db, refreshedHashes);

Impact
If a later step throws (e.g. validation failure), the sources are already marked processed, so a subsequent non-forced run reports "source cache unchanged" and skips live refetch. The impact is contained because the skip branch still reloads the cached bundle and re-runs the upsert, but the "processed" marker no longer means "successfully imported", which can mislead diagnosis of skip decisions.

Recommendation
Write the processed hashes only after the catalog transaction commits (the end of runWorStartupPipelineBody).

LowDone Warframe catalog-master sync runs hundreds of autocommit statements without a wrapping transaction

server/services/warframeSync.ts:780-850

Description
syncCatalogMasterFromSource() loops over all worksheets and items, calling upsert.run(...) and per-worksheet UPDATE ... SET active = 0 statements individually. Unlike the per-user sync (which uses codexDb.transaction(syncUser).immediate()) and refreshCatalogMasterMarketHrefs() (which wraps its loop in a transaction), this function has no transaction boundary.

Impact
Each statement commits separately (slower under WAL), and a crash mid-loop leaves the catalog master half-updated — e.g. some worksheets refreshed, others still holding the previous import's rows and active flags.

Recommendation
Wrap the whole function body in db.transaction(...)() for atomicity and a significant speedup.

Informational Any unhandled promise rejection shuts down the whole server

server/index.ts:564-569

Description
process.on('unhandledRejection', ...) calls shutdown(1). This is a deliberate fail-fast posture, and the long-running background jobs (WoR import, Warframe sync) do catch their own errors. It is worth being aware that any future stray rejection in a fire-and-forget path (e.g. the void refreshWorDbAvailability().then(...) boot chain) takes the service down rather than just logging.

Recommendation
Keep the fail-fast behavior, but audit new void someAsync() call sites for internal catches; the existing ones do this correctly.

Medium Warframe sync blocks the event loop with large synchronous per-user transactions

server/services/warframeSync.ts:1126-1316

Description
In execute mode each user's full reconciliation — worksheet creation, row adds/deletes, cell reconciliation across 11 worksheets, market-href refresh — runs synchronously inside one better-sqlite3 transaction on the main thread:

if (options.execute) {
  codexDb.transaction(syncUser).immediate();
} else {
  syncUser();
}
await new Promise<void>((resolve) => setImmediate(resolve));  // yields only between users

Impact
While a user with thousands of rows is being synced, the Node event loop is blocked: all HTTP requests (including /healthz) stall. The setImmediate yield between users bounds each stall to one user's transaction, and this is an admin-triggered batch job, so this is a scalability concern rather than a defect today.

Recommendation
If user counts or worksheet sizes grow, move sync execution to a worker_threads worker (better-sqlite3 supports separate connections per thread), or chunk the per-user transaction further.

Positive Observations

  • No SQL injection anywhere. Every query across server/ and all four packages is parameterized; the only dynamic SQL fragments are compile-time constants (lease TTLs), typed table-name unions ('catalog_heroes' | 'catalog_artifacts' | 'catalog_demons'), or generated ? placeholder lists.
  • Hardened image download pipeline (server/import/wor/images.ts): HTTPS-only host allowlist, credentials-in-URL rejection, redirect: 'error', 10 MB streaming size cap, magic-byte type detection (with HTML-masquerading-as-SVG rejection), and multi-layer path-traversal defenses (resolveWorImagePath plus checks in downloadImageToWorDir). Served SVGs get Content-Security-Policy: sandbox; script-src 'none' and X-Content-Type-Options: nosniff (server/index.ts:354-381).
  • Layered CSRF defense (server/index.ts:205-311): session-bound token compared with crypto.timingSafeEqual, Sec-Fetch-Site: cross-site rejection, and an Origin allowlist that only accepts HTTPS origins in production — plus a client helper that transparently refreshes and retries on token rotation (client/utils/api.ts).
  • Consistent per-user authorization in SQL: every read/write in all three game packages carries clerk_user_id or an ownership-verified account_id predicate; session-selected accounts are re-verified against the DB on every request (reconcileWorSessionAccount, resolveAccountId).
  • Strict, fail-fast configuration: production refuses weak SESSION_SECRET, encrypted-but-undecrypted Clerk keys, missing BASE_DOMAIN, and SECURE_COOKIES without TRUST_PROXY; NODE_ENV defaults to production (safe default); WOR_IMAGES_DIR is validated to stay inside DATA_DIR.
  • Privacy-aware admin telemetry: Warframe sync runs store only a SHA-256 initiator hash and masked user IDs (maskWarframeSyncResult), and the documented contract (sync-preview is POST + CSRF, admin-only) is implemented exactly.
  • The documented single-transaction guarantee holds: WoR catalog upsert, stale-entry deactivation, version bump, prune, and account sync run in one .immediate() transaction (startupPipeline.ts:362-402), matching AGENTS.md.
  • Solid test suite for domain logic: 25+ test files covering validation schemas, queries, sync canonicalization/arcanes/modular edge cases, session binding, auth routes, and the roster API, backed by a shared SQLite test harness.
  • Good operational hygiene: /healthz vs /readyz correctly separated (readiness checks all four DBs plus Armory readability), request-ID middleware with sanitization, graceful shutdown that waits for a running sync, rate limiting with sensible static-asset carve-outs, and helmet CSP scoped to Clerk + Turnstile origins.
  • Client quality: no dangerouslySetInnerHTML anywhere (imported wiki names are safely escaped by React), optimistic updates with correct rollback on failure, role="alert" on error surfaces, memoized table rows, and an SSE live-log stream for admin imports.
